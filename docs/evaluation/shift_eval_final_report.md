## 1. エグゼクティブサマリ

shift-scheduler-claudeは、**診療所特化・ゼロコスト・オフライン動作**という3つの差別化を持つシフト自動生成システムである。PuLP混合整数線形計画法によるスキル平均化、平易な日本語UI、ダブルクリック起動コンセプトは高く評価された（E.経営: ROI即時回収、月10-20h削減）。

しかし、**3つの致命的欠陥**がリリースを阻んでいる：

1. **スタッフ向け機能が一切存在しない**（B: 0/100点）― 希望提出・シフト確認・交代申請の全てが未実装
2. **Excel出力・印刷機能の欠如**（A）― 現場の「紙で配る」運用に対応できない
3. **労働基準法の週40時間チェック・36協定対応が未実装**（G: リスク度 高、E: 法的責任は経営者）

これら3点は**全てリリースブロッカー**であり、解消なくして実務投入は不可能である。一方で、バックエンドのアーキテクチャ設計（C: A-評価）、セキュリティの基本対策（F: SQL injection/XSS対策は優秀）、競合との差別化（E: 診療所特化は唯一無二）は高い完成度を示しており、上記課題を解消すれば**実務投入可能なMVP**となるポテンシャルは十分にある。

## 3. 致命的課題（リリースブロッカー）

以下の5件は**リリース前に必ず解消すべき課題**である。いずれも複数の視点から指摘されている。

### RB-1: スタッフ向け機能の完全欠如

| 項目 | 内容 |
|------|------|
| **深刻度** | Critical |
| **指摘視点** | B.スタッフ（主）, A.管理者, E.経営 |
| **内容** | 希望シフト提出、シフト確認、交代申請、通知機能が一切未実装。スタッフは口頭・紙でのやり取りを強いられる |
| **経営影響** | 人手不足の医療業界で「シフトの融通が利かない職場」は人材流出リスクに直結（E.経営レポート参照） |
| **対応案** | スタッフ用ログイン画面＋自分のシフト確認画面＋希望提出画面の3点セットをMVPとして実装 |

### RB-2: Excel出力・印刷機能の欠如

| 項目 | 内容 |
|------|------|
| **深刻度** | Critical |
| **指摘視点** | A.管理者（主）, E.経営 |
| **内容** | REQUIREMENTS.md:23に「Excel出力」と記載されているが未実装。印刷用レイアウトもなし |
| **経営影響** | 現場は「紙で配る」「ホワイトボードに貼る」運用が一般的。出力がなければシステムが使われない |
| **対応案** | openpyxlによる.xlsx出力、CSSの@media printによる印刷最適化 |

### RB-3: .exeファイルの未完成

| 項目 | 内容 |
|------|------|
| **深刻度** | Critical |
| **指摘視点** | A.管理者（主）, D.運用, E.経営 |
| **内容** | 「ダブルクリックで起動」がシステムの最大の売りだが、.exeのビルド・動作確認が未完了 |
| **運用影響** | エンドユーザーが開発モード（Flask + React）で起動するのは非現実的。Windows Defender誤検知問題もある（D.運用レポート参照） |
| **対応案** | PyInstallerビルド手順確立→動作確認→Windows Defender除外設定ガイド作成 |

### RB-4: 週法定労働時間（40時間）チェックの欠如

| 項目 | 内容 |
|------|------|
| **深刻度** | Critical（法令違反リスク） |
| **指摘視点** | G.法務（主）, A.管理者, E.経営 |
| **内容** | optimizer/engine.pyに週40時間超過を防ぐ制約がない。労基法第32条違反リスク |
| **法的リスク** | 6ヶ月以下の懲役または30万円以下の罰金（労基法第119条）。「AIが生成したシフトだから」は免責にならない（E.経営レポート参照） |
| **対応案** | optimizer/engine.pyのハード制約セクションに週労働時間制約を追加（G.法務レポートに実装イメージあり） |

### RB-5: 36協定対応の欠如

| 項目 | 内容 |
|------|------|
| **深刻度** | Critical（法令違反リスク） |
| **指摘視点** | G.法務（主）, E.経営 |
| **内容** | 時間外労働時間の記録・管理・上限チェック機能がない。要件定義書にも36協定関連要件の記載なし |
| **法的リスク** | 月45時間/年360時間の上限規制違反は罰則対象。長時間労働による健康被害リスクもある |
| **対応案** | overtime_recordsテーブル追加、時間外労働集計レポート機能を新規実装 |

## 7. 視点間の矛盾・トレードオフ

7つの視点を横断分析した結果、以下のトレードオフが確認された。

### T-1: セキュリティ vs ユーザビリティ

| 視点 | 主張 |
|------|------|
| F.セキュリティ | 認証・RBAC導入必須。DB暗号化必須。アクセス制御を強化すべき |
| A.管理者 | ITリテラシーの低いユーザーが主体。認証のステップが増えると使われない |
| E.経営 | 「ダブルクリックで起動」が最大の売り。認証は導入障壁を上げる |

**推奨判断**: ローカルデスクトップ用途ではF.セキュリティのPhase 1対応（CORS制限、SECRET_KEY、PII除去、ファイル権限）のみ実施。認証はスタッフ向けWeb機能を追加する時点で導入する。

### T-2: 機能充実 vs リリーススピード

| 視点 | 主張 |
|------|------|
| B.スタッフ | スタッフ向け機能（希望提出、確認、交代）を全て実装すべき |
| E.経営 | 早期にROIを実現したい。管理者ツールとして先にリリースすべき |
| C.開発者 | テスト不足のままの機能追加はリスク |

**推奨判断**: 管理者向けMVP（Excel出力＋.exe＋労基法チェック）を先にリリースし、スタッフ向け機能はPhase 2で段階的に追加する。

### T-3: 暗号化 vs パフォーマンス

| 視点 | 主張 |
|------|------|
| F.セキュリティ | SQLCipherでDB暗号化必須。医療PIIは平文保存不可 |
| D.運用 | パフォーマンス影響が懸念。小規模データでは問題ないが検証必要 |

**推奨判断**: まずベンチマークテストを実施し、SQLCipher導入前後の性能差を計測した上で判断する。

### T-4: オフライン vs モバイル対応

| 視点 | 主張 |
|------|------|
| D.運用、F.セキュリティ | オフライン動作が安全。ネットワーク露出を避けるべき |
| B.スタッフ、E.経営 | スマホからのシフト確認は現代のスタッフにとって必須。市場拡大にも必要 |

**推奨判断**: 管理者用=ローカルデスクトップ（オフライン）、スタッフ用=PWAまたはWeb（同一LAN内）のハイブリッド構成を検討する。

### T-5: 単一開発者 vs 保守性

| 視点 | 主張 |
|------|------|
| E.経営 | 開発者1名依存は最大の経営リスク。技術移管・保守契約が急務 |
| C.開発者 | ドキュメントは充実しているが、フロントエンドテストゼロは引継ぎ障壁 |

**推奨判断**: フロントエンドテスト追加（I-10）とE2E自動化（I-15）を優先し、引継ぎ可能な状態を作る。
