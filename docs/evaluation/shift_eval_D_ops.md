## 1. デプロイ容易性

### ✅ 良い点

- **単一実行ファイル配布**: PyInstallerで.exe化されており、非エンジニアでもダブルクリックで起動可能
  - `04-build/config/shift_scheduler.spec:114-129` - 単一EXE、コンソールなし、アイコン・バージョン情報対応
- **ビルドスクリプト完備**: `04-build/scripts/build.py` でワンコマンドビルド可能
  - テスト→フロントエンドビルド→EXE化→リリースパッケージ作成を自動化
- **リリースパッケージ自動生成**: ユーザーマニュアル・リリースノートも同梱される `04-build/scripts/build.py:120-148`
- **ポート競合チェック**: 既にポート5000が使用中の場合、明確なエラーメッセージを表示 `02-src/backend/main.py:147-168`
- **システムトレイ統合**: 非エンジニアでも終了操作が直感的（右クリック→終了） `02-src/backend/main.py:58-122`

### ⚠️ 不足点・問題点

1. **アップデート手順が未定義**
   - 現行版のアンインストール方法、データ移行手順、バージョンアップ時のDB互換性管理が不明
   - `04-build/README.md` にはビルド手順のみ、運用段階の更新手順がない
2. **依存ソフトウェアの記載不足**
   - CBC Solverがどのように同梱されているか不明（PuLPがデフォルトで持つか、別途同梱か）
   - `04-build/config/shift_scheduler.spec:29-68` に `pulp` は記載あるが、ソルバーの同梱方法が未記載
3. **Windows Defender問題の記載なし**
   - PyInstallerで生成した.exeは誤検知されやすい（スクリーンショット参照: `config/settings.yaml` のパスで殿が指摘した既存問題）
   - 配布時の署名方法、除外設定手順の記載がない
4. **ネットワーク要件が不明**
   - localhost:5000のみ使用と推測されるが、外部通信の有無（PuLP, npm等のライブラリ更新）が未記載
5. **ログローテーションが未実装**
   - `02-src/backend/utils/logger.py:33-36` で10MB・5世代のRotatingFileHandlerを使用しているが、メインログファイル `91-logs/shift_scheduler.log` は日時付きファイル名（`main.py:33`）で増え続ける可能性

### 🔍 未確定要件

- アップデート配信方法（手動配布 vs 自動更新）
- オフライン環境での動作保証（インターネット接続不要か）
- マルチユーザー環境での同時起動制御（現状はポート競合のみ）

### 💡 改善提案

1. **アップデートマニュアル作成**: バージョンアップ手順、データバックアップ→復元、DB移行スクリプトを `01-docs/manual/` に追加
2. **除外設定ガイド追加**: Windows Defenderの除外設定手順を `01-docs/manual/INSTALLATION.md` に記載
3. **コード署名の導入**: EV証明書でコード署名し、誤検知を回避（コスト・運用体制次第）
4. **CBCソルバー同梱の明示化**: `04-build/README.md` にPuLPのCBCソルバー同梱状況を記載、または明示的にバイナリ追加
5. **古いログファイルの自動削除**: `main.py` で生成される日時付きログファイルを定期削除するスクリプトを追加

## 2. データ管理

### ✅ 良い点

- **SQLite採用**: サーバーレスで運用コスト低、ファイルベースでバックアップが容易
  - `02-src/backend/models/database.py:24-36` - データディレクトリ自動作成、check_same_thread対応
- **自動バックアップ機能**: 日次自動バックアップ・7世代管理を実装 `02-src/backend/services/backup.py:20-23`
  - SQLite Online Backupを使用 `backup.py:81-88` → ファイルコピーより安全
- **バックアップメタデータ保存**: 各バックアップにJSON形式でタイムスタンプ・説明を記録 `backup.py:91-100`
- **復元前自動バックアップ**: 復元時に現行データを自動バックアップ `backup.py:165` → ロールバック可能

### ⚠️ 不足点・問題点

1. **SQLiteの同時アクセス限界**
   - 単一プロセス・単一ユーザー前提の設計。複数端末からの同時アクセスは不可
   - `database.py:35` の `check_same_thread=False` はマルチスレッド対応だが、複数プロセスからの書き込みには非対応
2. **バックアップディレクトリの固定**
   - EXE実行時は `EXE所在フォルダ/backups/`、開発時は `90-data/backups/` `backup.py:44-45`
   - 外部ストレージ（NAS、USBメモリ）への自動バックアップ設定がない
3. **データサイズ見積もりの欠如**
   - 何年運用すると何MBになるか、ディスク容量要件が不明
   - `90-data/shift.db` は65KB（初期状態）だが、職員100人×5年運用時の見積もりがない
4. **バックアップの暗号化なし**
   - 個人情報（職員名、スキルスコア、休暇情報）が平文で保存
   - `backup.py` にパスワード保護・暗号化機構なし
5. **データ移行ツールの不在**
   - 他システムからのデータインポート、エクスポート機能が不明
   - SQLiteファイルを直接操作する必要がある

### 🔍 未確定要件

- 複数拠点での利用時のデータ同期方法（現状は想定外）
- 法的保存期間（労務データの保管義務）への対応
- データ削除ポリシー（職員退職後のデータ保持期間）

### 💡 改善提案

1. **外部バックアップ設定**: 環境変数 `BACKUP_DIR` で外部ストレージパスを指定可能に（既に `backup.py:45` で対応済み、マニュアル記載不足）
2. **バックアップの暗号化**: 7z形式でパスワード保護、またはGPG暗号化を追加
3. **データ移行ツール提供**: CSV/Excelからのインポート、エクスポート機能を `99-input/` に追加
4. **容量見積もりガイド**: `01-docs/manual/` に「職員数×年数→ディスク容量」の目安表を記載
5. **複数拠点対応の検討**: 将来的にPostgreSQLやクラウドDB移行の設計検討（現状は非対応でOK）

## 3. 監視・障害対応

### ✅ 良い点

- **ログファイル出力**: `91-logs/` にログファイルを自動生成 `02-src/backend/utils/logger.py:15`
  - RotatingFileHandlerで10MB・5世代管理 `logger.py:33-36`
- **ITリテラシー低ユーザー向けエラーメッセージ**: 平易な日本語エラーメッセージを提供 `02-src/backend/utils/error_handler.py:7-66`
  - タイトル・メッセージ・解決策の3層構造で非エンジニアにも理解可能
- **ヘルスチェックエンドポイント**: `/health`, `/api/health` で稼働確認可能 `02-src/backend/app.py:77-85`
- **システムトレイでステータス可視化**: アプリケーション起動中は常に表示 `02-src/backend/main.py:181`

### ⚠️ 不足点・問題点

1. **ログレベルがINFOで固定**
   - `logger.py:18` で `level=logging.INFO` がハードコード
   - デバッグモード切り替えがない（開発時とリリース版で同じログ出力）
2. **アプリケーションログとシステムログの混在**
   - Flaskのログ、Optimizerのログ、ユーザー操作ログが単一ファイルに記録
   - 障害分析時にノイズが多い可能性
3. **リカバリ手順の未文書化**
   - ログに「ERROR」が出た場合の対処法、DB破損時の復元手順が不明
   - `error_handler.py` に「ログファイルを確認してください」とあるが、その後の手順がない
4. **パフォーマンスモニタリングなし**
   - PuLP処理時間、DBクエリ時間、メモリ使用量の記録なし
   - `optimizer/engine.py:372` で60秒タイムアウト設定はあるが、実際の処理時間ログなし
5. **アラート機能なし**
   - バックアップ失敗、最適化失敗時の通知機能なし（ログに記録されるのみ）

### 🔍 未確定要件

- 障害通知先（メール、Slack等）の必要性
- 監視ツール（Zabbix, Datadog等）との連携要否
- ログ保存期間の規定

### 💡 改善提案

1. **ログレベル環境変数化**: `LOG_LEVEL` 環境変数でINFO/DEBUG/WARNINGを切り替え可能に
2. **障害対応マニュアル作成**: `01-docs/manual/TROUBLESHOOTING.md` にエラーコード別対処法を記載
3. **パフォーマンスログ追加**: Optimizerの処理時間を `optimizer/engine.py:371-374` 前後で記録
4. **ログ分割**: アプリケーションログ・監査ログ（ユーザー操作）・エラーログを別ファイルに
5. **Sentry連携**: エラー時に自動でSentryにレポート送信（オプション機能として）

## 4. パフォーマンス

### ✅ 良い点

- **PuLP + CBC Solver採用**: 枯れた最適化ライブラリ、オープンソースで高速
  - `optimizer/engine.py:372` で60秒タイムアウト設定済み

### ⚠️ 不足点・問題点

1. **大規模データでの性能検証不足**

2. **CBC Solverのタイムアウト後の挙動**

3. **メモリ使用量の監視なし**
   - PuLP変数の生成数（`optimizer/engine.py:361`）はログに出るが、実際のメモリ使用量は記録されない
4. **DB接続プーリングなし**
   - `database.py:39-40` で `scoped_session` を使用しているが、複数リクエスト時の接続数管理が不明
   - SQLiteはファイルロックベースのため、接続プーリングの効果は限定的
5. **フロントエンドのビルド最適化**
   - Viteでビルドされているが、Tree-shaking・コード分割の設定が不明
   - `02-src/frontend/` 配下のビルド設定ファイル未確認

### 🔍 未確定要件

- 実運用での職員数・対象日数の上限（性能要件）
- スケールアップ時の対応方針（サーバー移行、クラウド化）

### 💡 改善提案

1. **ベンチマークテスト実施**: 職員10/50/100人×対象7/14/31日での処理時間・メモリ使用量を計測、`01-docs/` に記載
2. **準最適解の活用**: CBC SolverがタイムアウトしてもStatusが `Feasible` なら部分解を返す機能を追加 `optimizer/engine.py:379`

## 5. スケーラビリティ

### ✅ 良い点

- **モジュール分離設計**: バックエンド・フロントエンド・最適化エンジンが明確に分離
  - `02-src/backend/`, `02-src/frontend/`, `02-src/backend/optimizer/`
- **環境変数による設定変更**: DB_PATH, BACKUP_DIR等を環境変数で上書き可能 `backup.py:44-51`
- **REST API設計**: フロントエンドとバックエンドがAPI経由で通信 `02-src/backend/app.py:41-48`
  - 将来的にWebアプリ化・クラウド移行が可能

### ⚠️ 不足点・問題点

1. **単一拠点前提の設計**
   - localhost:5000固定、外部アクセス不可 `main.py:215`
   - 複数拠点（診療所A・B）でのデータ共有が不可能
2. **データベースのスケールアウト不可**
   - SQLiteはサーバーレスのため、複数サーバーへの分散が不可能
   - 職員数・データ量が増えた場合、PostgreSQL/MySQL移行が必要
3. **最適化エンジンのスケールアウト不可**
   - PuLPは単一プロセスで動作、並列計算非対応
   - 大規模データ時は処理時間が線形以上に増加する可能性
4. **マルチテナント非対応**
   - 複数診療所を管理する場合、診療所ごとにEXEを起動する必要がある
   - データベースの分離、ログの分離が必要
5. **クラウド移行時の障壁**
   - PyInstallerのEXE形式はWindows専用、Linux/macOS移行時に再ビルド必要
   - セッション管理、認証機構が未実装

### 🔍 未確定要件

- 将来的な複数拠点対応の必要性
- 職員数・データ量の増加見込み
- クラウド化・SaaS化の検討有無

### 💡 改善提案

1. **DB抽象化レイヤー導入**: SQLAlchemyを使用しているため、接続先を環境変数で切り替え可能に（PostgreSQL/MySQL対応）
2. **マルチテナント設計**: 診療所IDをテーブルに追加、単一DBで複数拠点を管理
3. **Docker化**: Dockerイメージでビルドし、クラウド移行を容易に（Windows EXE以外の配布形態）
4. **並列最適化の検討**: 複数の最適化モードを並列実行し、最良結果を選択（実装コスト大）
5. **クラウドソルバー連携**: Google OR-Tools Cloud等のクラウド最適化サービスと連携（コスト・保守性要検討）

## 6. セキュリティ（運用）

### ✅ 良い点

- **localhostのみバインド**: 外部からのアクセスを遮断 `main.py:215`
- **SECRET_KEY環境変数対応**: `app.py:33` で環境変数からSECRET_KEYを読み取り可能（本番環境で変更推奨）
- **SQL Injection対策**: SQLAlchemyのORMを使用、プレースホルダで自動エスケープ
- **CORS設定**: 開発時のみ有効 `app.py:38` → 本番では無効化（セキュリティ向上）

### ⚠️ 不足点・問題点

1. **Windows Defender誤検知リスク**
   - PyInstallerで生成した.exeは頻繁にマルウェア誤検知される
   - コード署名なしでは、企業環境で配布拒否される可能性
2. **個人情報の平文保存**
   - SQLiteファイル内の職員名・スキルスコア・休暇情報が暗号化されていない
   - `database.py:31` のDATABASE_URLに暗号化オプションなし
3. **認証機構の不在**
   - 誰でもアプリケーションを起動すれば全データにアクセス可能
   - ユーザー・権限管理なし
4. **ログの情報漏洩リスク**
   - `91-logs/shift_scheduler.log` に個人情報が記録される可能性
   - ログレベルINFO以上でも、エラー時に職員名等が含まれる可能性
5. **バックアップファイルのアクセス制御**
   - `90-data/backups/` 配下のファイルに対するACL設定なし
   - ファイルシステムの権限設定に依存

### 🔍 未確定要件

- 個人情報保護法・労働基準法への準拠確認
- 医療機関でのセキュリティポリシー（暗号化・認証）
- 監査ログ（誰がいつ何をしたか）の必要性

### 💡 改善提案

1. **コード署名の導入**: EV証明書でコード署名し、Windows Defender誤検知を回避
2. **SQLiteファイルの暗号化**: SQLCipherを使用してDB暗号化（パフォーマンス影響あり）
3. **認証機能追加**: 起動時のパスワード入力、または管理者/一般ユーザーの権限分離
4. **ログのサニタイゼーション**: 個人情報をログに記録しない、またはマスキング処理を追加
5. **セキュリティ診断**: OWASP ZAPやSonarQubeでセキュリティ脆弱性を診断（CI/CDに組み込み）
